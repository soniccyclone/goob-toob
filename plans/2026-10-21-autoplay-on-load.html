Goal

When a viewer opens a room link and the host is already playing, the video starts on its own, in sync, instead of sitting parked behind the native play button. The same path runs when the host presses play while a viewer is sitting unstarted on the page, and (in the playlist plan) when the room moves to the next video. The browser decides whether that start may have sound; the page tries audible first, falls back to muted with a visible "tap for sound" control, and only parks (today's behaviour) when the browser refuses even a muted start. The server does not change.

Depends on the test-lockdown plan (sc/start-action exists and is pinned) and the Playwright journeys plan: the browser matrix in Verification becomes journeys under lenient autoplay projects for Chromium and Firefox plus the strict ones, recorded in WebKit, with a real Safari spot check remaining manual.

Findings

How a viewer starts today

  • src/cljs/goob_toob/watch.cljs:186-199: on welcome the dash player is created with autoplay=false (player.cljs:17) and on streamInitialized the page calls park! (watch.cljs:44-53): pause, seek to the room's expected position with the epsilon nudge so a frame composites.
  • park! is called again on every state while unstarted (watch.cljs:100-101) and on every pong while unstarted (watch.cljs:226), so the parked frame tracks the room.
  • The play event is the join gesture (watch.cljs:281-303): with navigator.userActivation.isActive it sets started, seeks to expected and (if the viewer can control a paused room) sends cmd play; without activation it logs :play-rejected and re-parks. A programmatic video.play() fires the same play event, so today an autoplay attempt would be treated as a gesture-less press and parked by our own handler.
  • First-time viewers see the nick prompt; join! stores the nick and calls location.reload() (watch.cljs:399-403). The click on "join the goo" is a user gesture, and the reload throws it away: the new document has no activation.
  • The ready moment has three inputs that arrive in any order: welcome (room state), streamInitialized (player), first pong (clock offset, watch.cljs:214-226). Only after all three is expected-now trustworthy.
  • play! (watch.cljs:11-14) already swallows the rejection of a gesture-less play(); nothing inspects why it failed.

What browsers allow (the constraint this plan is built around)

  • Muted autoplay is allowed everywhere that matters (Chrome, Firefox, Safari incl. iOS with playsinline, which is already set at watch.cljs:240). This is the one reliable path.
  • Audible autoplay: Chrome allows it when the document has sticky user activation (any click on this document) or the user has interacted with the origin before (Media Engagement Index, or a click-initiated same-origin navigation such as the lobby link). Firefox allows it with sticky activation on the document. Safari is the strictest: a gesture on the element's own document, and Low Power Mode refuses even muted starts. I am confident about the muted rule and the sticky-activation rule in Chrome and Firefox; the Chrome navigation carry-over is likely but not something to rely on. The design relies on none of it: it tries, reads the rejection, and steps down.
  • play() returns a promise. Refusal is DOMException name NotAllowedError. AbortError means a pause() or source change interrupted the attempt; NotSupportedError is a media failure. Only NotAllowedError should trigger the muted retry.
  • A play() on a muted element then muted=false from a click works everywhere: the click is the activation.
  • Measured 2026-10-21 (Playwright plan): Playwright's Chromium, Firefox and WebKit builds all decode the H.264/AAC ladder, so every branch above can run under automation. The policy is forceable per launch in two of them: Chromium --autoplay-policy=user-gesture-required (strict) or no-user-gesture-required (lenient); Firefox media.autoplay.default 1 (block audible, allow muted: the shipped default) or 0 (allow). WebKit has no launch-time knob in Playwright, so its outcome is recorded, not forced. Chrome's navigation carry-over stays unmeasured (the journeys never navigate from the lobby with a gesture); it is a bonus in the field, never a dependency.

Plan

1 · sync_core.cljc: the decision gains :autostart

(defn start-action
  "What the watch page does with a start-related event. trigger is :play
  (the element fired play) or :state (room state, stream-ready or first
  pong). gesture? is navigator.userActivation.isActive at a :play.
  Returns :none, :park, :start, :start-room or :autostart."
  [trigger {:keys [started? gesture? playing? can-control?]}]
  (cond
    (not= trigger :play) (cond started? :none
                               playing? :autostart
                               :else    :park)
    started?             (if playing? :none :park)
    (not gesture?)       :park
    playing?             :start
    can-control?         :start-room
    :else                :park))

Only the first branch changes. A paused room still parks; a controller sitting on a paused room still has to press play (starting the room for everyone is a deliberate act).

2 · watch.cljs: autostart! with the step-down ladder

New state on st: "streamok" false (set true in the dash on-ready), "starting" false (an attempt is in flight), "automuted" false, "autostart" nil (the outcome: "audible", "muted" or "blocked"; goobProbe() from the Playwright plan reports it as :autostart). 

(defn- ready? [^js st]
  (and (.-room st) (.-player st) (.-streamok st) (seq (.-samples st))))

(defn- begin! [^js st video]
  (set! (.-started st) true)
  (set! (.-ourseek st) (ui/perf-now))
  (set! (.-currentTime video) (expected-now st (.-room st))))

(defn- autostart! [^js st token video unmute]
  (when (and (ready? st) (not (.-starting st)) (not (.-started st)))
    (set! (.-starting st) true)
    (begin! st video)
    (set! (.-muted video) false)
    (let [done (fn [muted?]
                 (set! (.-starting st) false)
                 (set! (.-automuted st) muted?)
                 (set! (.-display (.-style unmute)) (if muted? "" "none"))
                 (set! (.-autostart st) (if muted? "muted" "audible"))
                 (log! token :autostart {:muted muted?}))
          blocked (fn [err]
                    (set! (.-starting st) false)
                    (set! (.-started st) false)
                    (set! (.-autostart st) "blocked")
                    (log! token :autostart-blocked {:err (some-> err .-name)})
                    (park! st video))]
      (-> (.play video)
          (.then #(done false))
          (.catch (fn [err]
                    (if (= "NotAllowedError" (some-> err .-name))
                      (do (set! (.-muted video) true)
                          (-> (.play video)
                              (.then #(done true))
                              (.catch blocked)))
                      (blocked err))))))))

started is set before play() so the play event the browser fires for our own call lands in the "already started, room playing → :none" row of start-action, and so the policy loop takes over as soon as the first frame moves. On refusal it is unset and the page parks exactly as today.

A single dispatcher replaces the three scattered park! calls: 

(defn- settle! [^js st token video refs]
  (case (sc/start-action :state {:started? (.-started st) :playing? (:playing (.-room st))
                                 :can-control? (.-cancontrol st)})
    :autostart (autostart! st token video (:unmute refs))
    :park      (park! st video)
    nil))

Called from: the dash on-ready (after streamok is set and the res menu is built), the pong handler while unstarted, and apply-state-msg! when unstarted (so a host pressing play starts every parked viewer). While started is false and ready? is false it parks as before (the parked frame keeps tracking the room until the offset is known).

onplay uses start-action :play as the lockdown left it: "joined" (a gesture on an unstarted viewer sets started and logs :started) is decided in the handler, separately from the start-action result that says what the video does. One addition: if (.-starting st) is true the handler returns immediately (the event is ours).

The pause follow rule (watch.cljs:106-109) stays. play! stays for the host-driven play op when already started; with automuted still true the element is muted and play() succeeds without a gesture, which is the point.

Risks and open questions

  • Muted starts are the common case for returning viewers. A viewer who opened the link from a chat app, with a saved nick, will likely start muted and see "tap for sound". That is the standard web pattern and one tap; it is still better than a parked frame. If it grates, the fallback is a one-click "join" overlay on every visit, which is what we have today under a different name. Decide after seeing the field log mix.
  • Audio starts mid-sentence. Autostart seeks to the room position and plays; there is no fade. Accepted.
  • Safari Low Power Mode refuses muted starts: those viewers park and press play, exactly today's path. :autostart-blocked in the log says so.
  • The play event from our own play() and the onplay guard. Covered by setting started first and by the starting early return. If a browser ever fires play before the promise settles and after a refusal, the :none row is harmless (the element is paused anyway).
  • dash.js and muted. Muting the element does not affect dash.js buffering or ABR; it is an element property. The quality cap and the policy loop are unchanged.
  • Mount-in-place for the nick prompt changes page's shape slightly; client.cljs page-for still gets one node. No other caller.

Implementation notes

Implemented 2026-10-22 from this plan (steps 1-6), Chromium only for the journeys (Firefox and WebKit were dropped from the loop). Landed as specced, plus:

  • Playwright's evaluate hands the page user activation in all three engines: Chromium sends Runtime.callFunctionOn with userGesture: true, and trace DOM snapshots do the same. A scratch probe showed an audible play() refused under the strict policy (Chromium --autoplay-policy=user-gesture-required, Firefox media.autoplay.default 1, WebKit by default) with no evaluate, and allowed after a single page.evaluate or with snapshot tracing on. The strict projects therefore reported audible at first. Two fixes: the config keeps traces without DOM snapshots ({:mode "retain-on-failure" :snapshots false :screenshots true}), and party/open! takes :hands-off? true, which waits for the welcome from the socket frames, with party/wait-seen! watching socket frames and clientlog requests until the :autostart line arrives. Journeys that assert an autostart outcome open the viewer that way and only probe afterwards. The first-time-viewer journey still evaluates before its join click (the click is a real gesture anyway); its same-document marker is what catches a reload.
  • dash.js clobbered the autostart's seek. dash makes its own initial seek to the stream start after streamInitialized, so the room seek made at stream-ready was overwritten: a viewer joining 8 s in started at 0 and sat 7.9 s behind, catching up at 1.05x. ready? now also requires readyState > 2= (HAVE_CURRENT_DATA) and loadeddata runs settle!, so the start happens at the first frame rather than the next pong. Worst case (first pong after loadeddata while a park seek is in flight) waits for the next pong, up to 5 s.
  • One autostart attempt per load. settle! only autostarts while autostart is nil; after a blocked outcome it parks on every later trigger, as before this plan, instead of retrying on each pong and logging :autostart-blocked every 5 s.
  • Counters. begin! uses mark-seek!, so the begin seek counts in seeks; counters.autostarts counts attempts (the solo pause/play journey asserts it does not move). goobProbe() reports :autostart. automuted is set as specced but nothing reads it yet.
  • settle! returns its action and apply-state-msg! dispatches on it, so start-action stays the one decision for state messages.
  • Journeys changed for autostart: a late joiner parks on the live frame became a late joiner lands on the live frame (autostarts, strict muted, settled within :sync-within), and the parked-frame assertions moved to the new a viewer parks on a paused room. viewer joins a playing room in sync lost its parked phase and parked-drift assertion (an autostarting viewer never parks); everything else is kept and the metrics record gesture vs autostart. party/pair!, a dropped socket resyncs and throttled viewer steps the quality down no longer wait for a park before join!; join! waits up to :autostart-within for an autostart and only presses Space when none came. upload to lobby titles its upload by project, not engine: the second Chromium project found the first one's ready row and failed in 0.5 s.
