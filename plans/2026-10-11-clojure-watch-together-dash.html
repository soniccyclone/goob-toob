Goal

Build v1 of goob-toob from scratch: a self-hosted "watch together" video app, written entirely in Clojure (server) + ClojureScript (browser). The admin runs it on their own box, bulk-uploads their video library, and ffmpeg transcodes each file into multi-bitrate MPEG-DASH. The admin shares a room URL (over Tailscale or a port forward); friends open it and watch in near-perfect sync with a server-authoritative clock, a per-viewer resolution picker (auto or a locked height), catch-up after buffer stalls, and a lobby chat box where everyone joins under a temp nickname — all dressed in a gooey waterpark slime-green theme.

Plan

0 · Toolchain via podman (container/Containerfile, Makefile)

  1. container/Containerfile: FROM fedora, install java-25-openjdk-headless, nodejs, a full ffmpeg with libx264 (RPM Fusion or a static build), then the official Clojure CLI install script. One image serves dev and deploy. Build-time check: ffmpeg -encoders | grep libx264 must pass.
  2. Makefile: image (podman build), dev (podman run with the repo bind mounted, -p 8080:8080, storage dir mounted at /data, env vars passed, clojure -M:dev + shadow-cljs watch), run (prod), test, repl.

1 · Scaffold (deps.edn, shadow-cljs.edn, package.json)

  2. shadow-cljs.edn + package.json (devDep shadow-cljs, dep dashjs), :main builds resources/public/js/main.js.
  3. src/clj/goob_toob/config.clj: env-driven config — STORAGE_DIR (required, the admin's chosen video location), ADMIN_PASSWORD, PORT, transcode ladder + worker count.
  4. Layout:

2 · Repo layer (per ARCHITECTURE.org:11-12)

  1. db.clj: sqlite datasource (WAL mode), tiny SQL-file migration runner.
  2. repos/video.clj: videos table — id, title, original path, status (uploaded → transcoding → ready | failed), progress %, duration, ladder json, error text, timestamps.
  3. repos/room.clj: rooms — id, secret token, video id, created-by, created-at.
  4. repos/storage.clj: filesystem under STORAGE_DIR — uploads/<id>.<ext>, dash/<id>/manifest.mpd + segments; path-traversal guards, free-space check before upload.

3 · Upload + ffmpeg → MPEG-DASH pipeline (services/transcode.clj)

  1. POST /api/admin/videos accepts multipart, streams to uploads/, inserts a video row, enqueues a job. Bulk = multiple files in one form post.
  2. Job queue: core.async channel + worker pool (default 1 worker so encoding doesn't starve serving; nice the ffmpeg process).
  3. ffprobe -print_format json for duration/streams; ladder default 1080/720/480/360 + aac audio, all H.264 so dash.js ABR can switch freely.
  4. One ffmpeg pass per video producing the whole DASH tree:
ffmpeg -hide_banner -nice 10 -i "$IN" \
  -filter_complex "[0:v]split=4[s0][s1][s2][s3];[s0]scale=-2:1080[v0];[s1]scale=-2:720[v1];[s2]scale=-2:480[v2];[s3]scale=-2:360[v3]" \
  -map "[v0]" -map "[v1]" -map "[v2]" -map "[v3]" \
  -map 0:a:0 -map 0:a:0 -map 0:a:0 -map 0:a:0 \
  -c:v libx264 -preset veryfast -profile:v high -pix_fmt yuv420p \
  -g 240 -keyint_min 240 -sc_threshold 0 \
  -b:v:0 6000k -b:v:1 3000k -b:v:2 1200k -b:v:3 600k \
  -c:a aac -b:a 128k \
  -f dash -seg_duration 4 -use_template 1 -use_timeline 0 \
  -adaptation_sets "id=0,streams=v id=1,streams=a" \
  -progress pipe:1 -y "$STORAGE_DIR/dash/$ID/manifest.mpd"

Exact flags get tuned during implementation; the point is one pass, one manifest, GOP-aligned keyframes at segment boundaries so ABR switching is clean. -progress output is parsed to update the video row's % complete.

  1. Status transitions + failure capture (tail of stderr into the row). KEEP_ORIGINAL env decides whether the source file survives.

4 · HTTP API + static serving (routes.clj)

  1. reitit routes: admin login (password → session cookie), admin middleware; GET/POST /api/admin/videos, DELETE /api/admin/videos/:id; GET /api/videos (public list for the lobby), POST /api/rooms (admin creates a room → returns /watch/<token> URL to hand to friends).
  2. DASH serving: GET /dash/:video-id/manifest.mpd (application/dash+xml) and GET /dash/:video-id/:seg with correct types and HTTP Range support (ring's resource-ranges middleware covers it).
  3. Static: shadow-cljs output + css via ring-resource-data.

5 · Sync service — server-authoritative room clock (ws.clj, services/sync.clj)

  1. ring-websocket endpoint /ws/room/:token; the room token in the URL is the only viewer credential.
  2. Room state = one atom per room: {:video-id :pos :t0 :playing? :rate} where pos is media seconds at monotonic instant t0. Expected position for any client = pos + (now − t0) · rate.
  3. Messages: hello (join, nick), ping/ping-ack (clock-offset estimation), host commands play/pause/seek/select-video, heartbeat broadcast every 2 s, chat, and a viewer status report (local pos, buffering) every 5 s so the admin sees who is lagging.
  4. Host = the room creator (admin) in v1. Viewer messages are chat + status only. Server broadcasts every state change immediately.
  5. All timing on System/nanoTime monotonic clocks; wall clock never used for sync math.

6 · Frontend — CLJS + dash.js (src/cljs)

  1. player.cljs: thin dash.js wrapper. Resolution menu: auto → ABR on (recommended, best sync); a fixed height → autoSwitch=false + lock the matching Representation. Choice persisted per browser in localStorage.

  2. sync.cljs — pure, unit-testable functions: offset estimate from ping RTT samples (min-RTT, NTP-style); drift = local − expected; policy:

    drift action
    abs < 0.3 s nothing
    0.3–1.5 s playbackRate nudge ±5 % until < 0.15 s
    abs > 1.5 s hard seek to expected
    stalled (buffering) do nothing until recovery, then policy

    The last row is the catch-up feature: the room never pauses for one buffering viewer; when their buffer refills the policy snaps them back.

  3. ui.cljs: lobby (video grid, join/create), watch page (player + resolution menu + chat box — the one DOM-heavy area per ARCHITECTURE.org:18-21), admin page (storage dir display, en-masse upload with per-file job status, library management, room creation + copyable link).
  4. Nickname on join: first open of a room link shows a join overlay asking "who are you?"; the name is a temp handle kept in localStorage (pre-filled next time, re-editable), sent in the WS hello, and shown on chat messages + the participant list. The participant list is also the admin's "who's lagging" view (fed by the 5 s status reports). No accounts — the name is cosmetic, not an identity.
  5. Vanilla-DOM style per ARCHITECTURE.org:19 — plain CLJS DOM interop, no SPA framework; pages are static HTML, CLJS hydrates and patches only what changes.
  6. Theme — gooey waterpark slime (hand-written resources/public/css/theme.css, CSS custom properties, no CSS framework):
    • Palette: deep teal-black water background (#07231F), slime/lime green primary (#8FE032), aqua-turquoise splash accent (#1FC8DB), foam white text; no orange anywhere.
    • Gooey: blobby rounded buttons that merge/stretch on hover (SVG gooey blur-contrast filter), dripping-blob accents, wavy section dividers; waterpark: aqua gradient washes, pool-tile texture behind the lobby grid, bubble animation in the chat box.
    • Player chrome stays dark + minimal so video colors aren't tinted; the slime goes on the chrome around it (headers, buttons, chat, badges).

7 · Auth + deploy docs

  1. Auth: single admin password from env, session cookie, /api/admin/* middleware. No user accounts; room URL = capability. Room tokens are long random strings; admin login is rate-limited per IP — this matters because Funnel puts the whole internet one guess away from the login form.
  2. README.org sharing options, in order of preference:
    • Tailscale Funnel (the "send a link to friends" path): tailscale funnel 443 publishes the app publicly at https://<machine>.<tailnet>.ts.net with free TLS — friends need no Tailscale install, just the link. One-time: enable Funnel in the Tailscale admin console; Funnel fronts only ports 443/8443/10000.
    • Tailscale Serve (private): friends must run Tailscale and be in your tailnet; use for housemates/family machines.
    • Raw port forwarding: last resort, ships video + chat unencrypted.
  3. Update ARCHITECTURE.org: gstreamer → ffmpeg, record the layering this plan implements.

Risks and open questions

  • ARCHITECTURE.org:15 says gstreamer; you said ffmpeg. Plan follows ffmpeg and updates the doc. Say the word if gstreamer was actually meant.
  • "MUST be clojure+clojurescript": assumed to allow dash.js as an npm library (shadow-cljs npm support). Hand-rolling a DASH client (manifest parse, ABR, segment fetch/buffer via MSE) is CLJS-only but multiplies the scope — needs your call before building.
  • Host model assumed: the admin who creates a room is the sole playback controller; viewers watch + chat. No "everyone drives" mode in v1.
  • Auth assumed minimal: one admin password via env; room URL is a secret capability; nicknames are cosmetic, not identity. Funnel = the app is publicly reachable, so the password + room tokens are the entire defense (hence rate limiting + long random tokens); Serve mode or raw forwarding without TLS is weaker still.
  • Host ffmpeg lacks libx264 (verified) → the container image must ship a full ffmpeg; make image fails loudly if it doesn't.
  • Encoding on the same box that serves streams: CPU contention mid-party. Mitigated by 1 transcode worker + nice + veryfast; transcode before the party is the documented workflow.
  • Room state is in-memory; a server restart drops live rooms (DB rows survive). Acceptable for v1.
  • use_timeline 0 + segment templates assumes dash.js template handling; exact dash muxer flags get tuned against a real clip early (step 3 is deliberately before the frontend).
  • Ladder assumes one audio track; multi-audio/subtitles deferred.
