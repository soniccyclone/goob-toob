* Goal
A small suite of end-to-end tests drives goob-toob the way a party does:
real Chrome, real dash.js, real H.264 segments from the real transcode,
real websockets, two or three browser contexts in one room. Each journey
samples a metrics probe on the page and the server's own view of the room,
and asserts summaries of those series (drift after settle, seeks, stalls,
rate bounds, time to sync) against one thresholds table. The suite runs
locally in a container (=make e2e=) and as its own CI job, and writes a
metrics table into the job summary so a run says more than pass or fail.
Once it is green in CI, the JVM suite shrinks to what a browser cannot
reach: pure math, adversarial protocol input, migrations, and failure
modes. This plan comes before autoplay and playlists; both then add
journeys here instead of manual verification lists.

* The thesis, and where it holds
Nathan's framing: most of the truly valuable tests of this repository
could be a small set of Playwright journeys asserting on metrics, with
more granularity than pass/fail and none of the drift of unit tests that
pin implementation. Taking that seriously:

- *It holds for everything user-facing.* The product is "watch in sync".
  Its value is measurable: drift, stalls, seeks, catch-up rate, time to
  join. Those are properties of the whole system (server clock, websocket,
  dash.js buffering, the element's =playbackRate=, Chrome's autoplay
  policy) and no JVM test touches more than one of them. The lockdown's
  HTTP and websocket wiring tests prove the server speaks the protocol;
  a journey proves the party works. When both exist, the wiring tests are
  the ones that break on harmless refactors.
- *It does not hold for three kinds of test, which stay on the JVM.*
  1. Pure logic with many branches (=policy=, =room-rate=, =quality-cap=,
     =ladder-for=, =parse-range=). A journey samples them under one real
     condition with wide tolerances; a table test covers every branch in
     milliseconds. This is the one place unit tests are the right tool,
     and =cljc= was built for it.
  2. Adversarial and security input: a viewer sending =cmd= without
     control, a string =pos=, a non-object frame, path traversal, the
     login limiter, the two-port split. A browser journey can reach some
     of these through =page.evaluate= and a raw =WebSocket=, but they are
     protocol tests wearing a costume. Keep them where they are cheap and
     exact.
  3. Time and failure: the 180 s give-up window, a crashed transcode's
     error text, a missing original, migrations on an old database. Not
     affordable or not reachable from a browser.
- *Metrics are the right assertion language for a sync product*, with one
  discipline: thresholds live in one data file, assertions are on
  summaries over a window (p95, max after settle, counts), never on a
  single sample, and every journey writes its series to disk so a
  regression shows as a number moving before it shows as a failure.

Verdict: build the journeys, then retire the JVM tests that only pin
wiring (list in Decisions). The suite that remains is about 85 JVM tests
of logic and hostility plus about a dozen journeys of value.

* Findings
- *Nothing browser-driven exists.* =test/= is Clojure only; =package.json=
  has dash.js alone; no Chrome on the host. Every plan's browser
  verification so far was manual in two tabs.
- *Playwright's bundled Chromium cannot play our video.* Open-source
  Chromium ships without H.264 or AAC; the ladder is libx264 and AAC
  (~src/clj/goob_toob/services/transcode.clj:87-93~). Playwright supports
  the =chrome= channel (branded Google Chrome, all codecs). GitHub's
  =ubuntu-latest= image has Google Chrome preinstalled; the Fedora test
  image needs Google's rpm repo. Firefox and Safari stay manual.
- *Autoplay policy is a launch flag.* Chrome's
  =--autoplay-policy=user-gesture-required= (strict, the real-world
  default) and =no-user-gesture-required= make the autoplay plan's three
  branches deterministic per Playwright project. Nothing in the suite
  depends on Chrome's own history heuristics.
- *Network shaping is available.* Playwright has no throttle API, but on
  Chrome a CDP session gives =Network.emulateNetworkConditions=
  (throughput, latency), enough to make a laggard and trigger the quality
  cap.
- *The page already measures everything.* =st= on the watch page
  (~src/cljs/goob_toob/watch.cljs:387-389~) holds =offset=, =mode=,
  =qcap=, =started=, =buffering=; =expected-now= (~watch.cljs:38-42~) and
  =buffer-ahead= (~watch.cljs:55-60~) compute the rest. The =clientlog=
  path (~routes.clj:140-145~) already ships =:seek-back=, =:stalled=,
  =:quality-cap=, =:started= events to the server log. Nothing is
  exposed to a test.
- *The server already measures every client.* =rooms*=
  (~src/clj/goob_toob/services/sync.clj:12~) holds per-client =:drift=,
  =:at=, =:buffering=, =:behind-since= and the room's =:rate=,
  =:playing?=; =client-drifts= (~sync.clj:93-96~) derives ages. There is
  no read endpoint.
- *Upload and transcode are reachable over HTTP* (~routes.clj:102-114~)
  with the admin session; =make clip= shows the lavfi recipe for a
  synthetic clip. A 10 s 1280x720 clip transcodes to three rungs in a few
  seconds in the container.
- *The join gesture.* Chrome toggles playback when a =<video controls>=
  surface is clicked, and a Playwright click is a real user activation.
  If headless Chrome does not toggle on surface click, focusing the
  element and pressing Space does the same with activation.
- *CI today* (~.github/workflows/ci.yml~): =test= (JVM + build smoke),
  =tag= (release on main), =plans= (Pages). The =test= job already installs
  Java, Clojure, Node and ffmpeg.

* Decisions
Each with the evidence; Nathan flips what he disagrees with.
- *Specs are plain JavaScript (ESM) under =e2e/=.* The project is 100 %
  Clojure/CLJS and that rule stands for product code. =@playwright/test=
  is a runner with its own module discovery and top-level =test()=
  registration; driving it from shadow-cljs (=:npm-module= target, one
  compiled file per spec, a second build in the loop) buys nothing but a
  compile step for about 400 lines of harness. If this grates, the
  reversible path is a later shadow build that emits the same files.
- *Chrome channel only.* See Findings. Firefox and Safari remain in the
  autoplay plan's manual matrix.
- *One metrics probe in product code.* =watch.cljs= exposes a read-only
  =window.goobProbe()= returning the page's view (below). It is also a
  support tool: paste it in devtools on a user's machine. Cost: a few
  lines and an unreleased counter object.
- *One read endpoint on the admin API.* =GET /api/admin/rooms/:id/live=
  returns the live room: =:pos :t0 :playing :rate :now= and every client's
  =:nick :drift :age-ms :buffering :behind-ms=. Admin-only, loopback on
  desktop. The authority's own numbers are what the room acts on, so
  journeys assert on both the page and the server.
- *Thresholds are data.* =e2e/thresholds.js= exports one object; specs
  import names from it; no numeric literal in a spec. Per-journey series
  go to =e2e/metrics/<spec>-<title>.json=; CI uploads them and prints a
  table to the job summary.
- *Each journey makes its own room; the clip is shared.* Global setup
  logs in, generates the clip with ffmpeg, uploads it, waits for =ready=.
  Rooms are cheap and isolate state.
- *Local loop is a container*, =container/Containerfile.e2e= on top of the
  test image, with =make e2e=. CI is the confirming run.
- *Retire wiring tests after five green CI runs*, in a follow-up PR that
  this plan names (below). Not in the same PR: a journey that is flaky on
  the runner must not take a working test with it.
- *Soft metrics first for the throttled journey.* Bandwidth shaping on a
  shared runner is the least deterministic thing here; its numbers are
  recorded and printed for a few runs before any threshold is asserted.

  drift stats computed only after =settleMs=.

  =metrics/<file>-<title>.json= and attaches the summary to the Playwright

  endpoint.
*** =thresholds.js= (initial values; tune from the first recorded runs)
#+begin_src javascript
export const T = {
  startWithin:      5_000,  // ms from click to started
  parkDrift:        1.0,    // s, parked frame vs room before joining
  syncWithin:       8_000,  // ms until |drift| < settled after joining
  settled:          0.5,    // s
  steadyP95:        0.5,    // s over the sampled window after settle
  pauseAgreement:   0.3,    // s between two paused elements
  catchRate:        [1.04, 1.06],
  nudgeRate:        [0.94, 0.96],
  roomSlowRate:     0.97,
  roomSlowWithin:   4_000,  // ms from laggard status to rate 0.97 at the server
  closingMin:       0.02,   // s of drift recovered per s while catching up
  resyncWithin:    15_000,  // ms after the network returns
  chatWithin:       2_000,
};
#+end_src

* Risks and open questions
- *Timing on shared runners.* The sync journeys measure seconds of
  wall-clock behaviour. Mitigations: =workers: 1=, one retry in CI,
  summaries over windows with a settle period, thresholds tuned from
  recorded runs before being tightened, and the throttled journey kept
  soft. A journey that flakes twice gets its threshold loosened or its
  assertion moved to recorded-only, never a sleep.
- *Headless Chrome and the click-to-play surface.* Fallback is Space on
  the focused element; both are activations. If neither toggles in
  headless, the host can start the room through its own play button
  (that path exists today) and viewers join through Space.
- *H.264 decode in headless.* Branded Chrome decodes in software without
  a GPU; expect it to be fine at 720p. If the runner drops frames,
  =currentTime= still advances and the metrics hold; the clip can also
  be generated at 480p.
- *Chrome in the Fedora image* adds about 300 MB and a Google repo. It is
  a separate image (=e2e-image=), so =make test= is unchanged.
- *The probe is product code.* It is read-only and unlisted; it costs a
  closure. Counters are the only new state.
- *Twelve seconds of clip* bounds every journey; the pause-and-seek
  journey seeks to +30 s on a 12 s clip, so make the clip 60 s (still a
  few seconds to transcode) or seek +5 s. Decide at implementation; the
  plan says 60 s.
- *=reuseExistingServer= locally* lets an already running =make dev=
  server be reused on =18080=; the storage dir must then match. The
  default =make e2e= path always starts its own.
- *The retirement list shrinks coverage of the admin HTTP API to the
  journeys.* If the admin console is ever replaced, those journeys go
  with it and the API loses its tests. Accepted; the API's consumer is
  the console.
